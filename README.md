# GrantDeck

GrantDeck offers a self-service web portal for retrieving API bearer tokens. It is intended for cases where JWTs are not an option, such as with LLM client tooling. GrantDeck offers a authz endpoint for generated tokens that can be integrated into reverse proxies. 

GrantDeck defines the following basic concepts:

- User: A natural person, in possession of an OAuth login.
- Bearer token: A secret string generated by a user. Tokens are bound to projects.
- Resource: A URL that has access protection through tokens. Resources are bound to projects.
- Project: A collection of users that can access a collection of resources.
- Project administrator: A user who can configure the project membership of other users.
- Superuser: A user that manages projects and resources.

The guiding principle of GrantDeck is that data lane and control lane are not the same. API traffic should not flow through a web application, just for the purpose of authorization checks. A reverse proxy should handle the data traffic directly, and delegate the authorization to some other entity. 

Our guiding example is the combination of Enovy, AI Gateway and GrantDeck to implement a self-management authorization scheme for HTTP APIs.

## Configuration

GrantDeck starts in production mode by default. For local development, set:

```env
GDK_ENV=development
```

Development mode enables a local SQLite database, a dev-only secret key, and `DEBUG=True` defaults. 
You can use `manage.py createsuperuser` in combination with the `/login/admin` endpoint to try the software locally without configured OAuth provider.

## Health checks

Use `/healthz/` for liveness checks. It returns `200 OK` when Django can serve the request.

Use `/readyz/` for readiness checks. It returns `200 OK` when the database is reachable, and `503 Service Unavailable` otherwise.

OAuth provider reachability is not part of readiness checks, since OAuth outages affect only new SSO logins.

## Container image

Build the production image from the project root:

```bash
docker build -f deploy/Dockerfile -t grantdeck:local .
```

The image uses `cgr.dev/chainguard/python:latest` as runtime base image and intentionally does not provide a shell. Django management commands still work directly:

```bash
kubectl exec deploy/grantdeck -- python manage.py showmigrations
```

On startup, the container runs database migrations and then starts Gunicorn on port 8000. In deployments with multiple replicas, avoid starting several schema-changing revisions at the same time.

## Kubernetes

The `deploy/k8s/overlays/production` Kustomize overlay deploys GrantDeck with SQLite on a 1 Gi PVC and attaches an HTTPRoute to an existing Gateway API Gateway. The Gateway is expected to terminate HTTPS. The deployment uses one replica because SQLite and the PVC are single-writer, and migrations run at container startup.

Create the local credentials file and replace both placeholder values:

```bash
cp deploy/k8s/overlays/production/secret.env.example deploy/k8s/overlays/production/secret.env
```

Set a strong random `GDK_SECRET_KEY` and the OIDC client secret. `secret.env` is gitignored. Then edit `config.env` in the same directory for the OIDC issuer and client ID. Set `K8S_NAMESPACE`, `ROUTE_HOST`, `ROUTE_PREFIX`, `GATEWAY_NAME`, `GATEWAY_NAMESPACE`, `GATEWAY_SECTION`, `PVC_SIZE`, and `IMAGE` in `config.env` to match your cluster. Keep `GDK_ALLOWED_HOSTS` and `GDK_CSRF_TRUSTED_ORIGINS` aligned with the route hostname. For a non-root prefix such as `/grantdeck`, set both `ROUTE_PREFIX` and `GDK_SCRIPT_NAME` to `/grantdeck`.

To grant Django administrator access to an OIDC account, set `GDK_OIDC_ADMIN_USERNAME` in the generated ConfigMap input. When that username completes OIDC login, GrantDeck promotes the account to superuser and staff. No shell access or local password is required.

Render and apply the resources with:

```bash
kubectl kustomize deploy/k8s/overlays/production
make deploy
```

The configured `K8S_NAMESPACE` must already exist. The cluster must have the Gateway API v1 CRDs installed and an existing Gateway with a listener that accepts routes from that namespace. `make deploy` applies the overlay. Kustomize generates hashed ConfigMap and Secret names and updates the Deployment references when their inputs change.

## Envoy authorization

GrantDeck is intended to work as AuthZ endpoint for reverse proxies. The project currently focusses on Envoy and AIGateway als primary counter parts.

Envoy HTTP external authorization is expected to call `/authz/check` with the `path_prefix` setting, not `path_override`. Envoy keeps the protected request path visible to GrantDeck in that case:

```text
protected request: GET https://api.example.com/api/models
authz request:     GET /authz/check/api/models
checked resource:  https://api.example.com/api/models
```

GrantDeck returns the authenticated user in the `x-current-user` HTTP header and the project shortcut in the `x-current-project` HTTP header, so both must be enabled in the `allowed_upstream_headers` block for `authorization_response` accordingly.

GrantDeck reconstructs the checked URL from the auth request scheme, host, and stripped path. It always uses `X-Forwarded-Proto` and `X-Forwarded-Host`, so configure Envoy to pass values that represent the original client request.

## Architectural principles

The coding guidelines are intended for coding agents and human collaborators:

- Prefer standard Django features over custom code.
- Use external packages only when they remove more code than they add.
- Keep code small and direct. Avoid speculative abstractions, decorative helpers, and unused flexibility.
- Put data-related control flow on model classes or model managers.
- Keep views thin. 
- Keep the frontend view focused on end-user self-service. Administrative acitivies belong into Django admin.
- Make production the safe default. Development mode must be enabled explicitly with `GDK_ENV=development`.
- Store full secrets only as hashes.
- Bearer tokens always have a life-time.
- Log security decisions explicitly, especially authorization results. Make the live easier for admins running this product.
- Tests should use pytest and focus on functional behavior, permissions, and security decisions. UI tests should be kept minimal.
- Tests are located in a "tests" folder.
- Keep user-facing names such as "Bearer token" consistent.
- Avoiding custom prefetch machinery is more valuable than minimizing query count.
